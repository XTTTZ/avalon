# 规则、状态与安全设计

## 权威状态机

`lobby → reveal → team → teamVote → questVote → team / lady / assassination / finished`。

全部规则只在 `server/engine.ts` 执行，浏览器提交意图。UI 不能指定身份、阵营、当前阶段、投票结果或获胜者。任务结束由最后一张合法任务票的事务自动推进，不依赖房主在线。队长按座位轮换，初始队长随机。确认身份须全员完成；组队严格过半才通过，平票拒绝。

房主通过 `reorder` 提交全部玩家 ID 的无重复排列，或通过 `shuffleSeats` 在服务端随机排列；大厅和局中均可操作，刺杀和结算后不再组队。只改变 `players` 的顺序及连续座位号，不改变当前队长、玩家 ID、会话、已投票或笔记归属。新成员追加在末位，离开/踢人后保持其他人的相对顺序。再开一局保留座位排列和带队方式。

`leaderMode` 默认为 `rotation`：首位队长随机，之后沿座位排列循环。`manual` 模式首次及每次轮换后队长留空，等待房主指定；队长为空时任何玩家均不能提交队伍。`assignLeader` 可在确认身份/选人阶段立即指定当前队长，更新 phaseKey 阻止旧队长的在途提名；投票/湖中仙女阶段只可指定 `nextLeaderId`，不会清空或重做投票。预约在下次轮换时消费一次，之后恢复相应模式，支持连续指定同一玩家和取消预约。手动首位队长确定时才初始化湖中仙女，之后改序/换队长不改变已持有的标记。旧房间缺少新增字段时按自动循环、无预约解释。

前端根据公开排列、模式、当前队长及预约显示队列；预约会覆盖下一任预测，手动模式显示等待指定，不在渲染时重新随机。所有改序和指定仍受房主权限、版本和请求幂等校验保护。

标准阵营人数与任务人数：

| 人数 | 善 / 恶 | 五轮任务人数  |
| ---- | ------- | ------------- |
| 5    | 3 / 2   | 2, 3, 2, 3, 3 |
| 6    | 4 / 2   | 2, 3, 4, 3, 4 |
| 7    | 4 / 3   | 2, 3, 3, 4, 4 |
| 8    | 5 / 3   | 3, 4, 4, 5, 5 |
| 9    | 6 / 3   | 3, 4, 4, 5, 5 |
| 10   | 6 / 4   | 3, 4, 4, 5, 5 |

三次任务成功后刺杀梅林，三次任务失败邪恶胜，连续五次组队拒绝邪恶胜。7 人以上第四轮须两张失败票。善良只能提交成功，邪恶可选成功/失败。参考原版出版规则扫描：[The Resistance: Avalon](https://avalon.fun/pdfs/rules.pdf)。

自定义支持 5–12 人，邪恶至少一人且少于一半；特殊角色至多一张，忠臣/爪牙可重复。梅林和刺客成对启用，派西维尔需要梅林。总轮数 3–9；获胜任务数 `w` 为 2 到 `floor((总轮数+1)/2)`，确保在最多 `2w−1` 轮内决出任务胜负，后面的配置轮次可能不使用。每轮人数 1 到总人数；失败门槛不超过本轮人数和邪恶人数；拒绝上限 1–10。11–12 人默认 4 恶，其余善，任务人数 3/4/5/6/6，属于本应用扩展。

## 知情边界与扩展

- 梅林看到开局邪恶玩家，但不见莫德雷德；看得到奥伯伦。只知邪恶，不知具体角色。
- 派西维尔看到梅林和莫甘娜组成的候选集合。其他角色没有这份集合。
- 刺客/莫甘娜/莫德雷德/爪牙互认邪恶，但不知道同伴具体角色；不见奥伯伦。奥伯伦不知道同伴。
- 湖中仙女标记初始给首位队长前一席。第 2/3/4 次任务结束且未触发胜负/刺杀时查验一名从未持有过标记的玩家。查验人得到当时阵营，目标成为下任持有人。公开谁查了谁，不公开结果。
- 兰斯洛特明确采用本应用扩展：一善一恶成对加入，彼此互认，不参与其他邪恶的互认。梅林看到初始邪恶兰斯洛特。开局线索不随阵营变化更新。
- 固定模式不换阵营；变化模式从第三轮开始，在组队前公开抽取变化牌（3 张不变、2 张交换，耗尽后重洗）。交换两人当前阵营，不改变角色名称。任务票权限和胜利阵营取当前阵营；湖中仙女记录查验当时阵营。

## 数据与并发

PostgreSQL 环境使用 `PostgresStore` 与仅 service_role 可调用的 RPC。`avalon_commit` 在一个 SQL 事务中按键排序加锁、核对全部读取的 UUID 修订号、统一提交写入；缺失键同样加锁，删除重建产生新 UUID。冲突最多重跑 8 次，之后返回可重试的 CONFLICT；失败回调只核验读取，不写入。表及 RPC 对 PUBLIC、anon、authenticated 撤销权限，服务端 Key 只存在于云函数中。本地和文档数据库适配器保留原实现。

`shared/types.ts` 是白名单响应契约；`shared/rules.ts` 只有公开规则。`server/engine.ts` 的 RoomState 含服务端秘密，绝不直接返回。`projectRoom` 按可信 userId 生成公共状态和本人视图。前端没有 CloudBase 数据库 SDK，所有集合客户端读写规则为 false。

API 的 `userId` 从服务端签名会话提取，玩家公开 playerId 为独立随机 ID。所有非登录操作检查身份与房间成员资格。房主只有配置、开局、终止等权限，不继承他人秘密与笔记权限。结算才返回全桌角色；任务票的玩家映射在每次任务结束立即删除。

云端 `runTransaction` 串行化并发冲突，房间状态、去重回执、必要的用户记录同事务更新；本地 FileStore 用串行队列和原子文件替换实现同样语义（只用于单进程开发）。普通命令必须匹配版本和 phaseKey；ready/组队票/任务票可在同一阶段并发提交，不允许把旧阶段的票投到新阶段。请求 ID 去重，重复请求重新生成当前权限投影，不返回旧身份快照。票投出后不可修改。任务票原文不写客户端持久存储、应用日志或公开历史。

新房间号在 `1000–9999` 中使用密码学随机数生成，以房间号为数据库文档主键。同一事务读取该主键、确认不存在、创建房间并保存用户回执；并发碰撞由事务重试处理。占用时换号，最多尝试 32 次后返回可重试错误，绝不使用覆盖写入作为兜底。已过期但尚未清理的文档仍占用号码；清理删除后才可复用。接口继续接受已有六位房间号，不迁移或重编号进行中的对局。

笔记文档按 `roomCode + ownerUserId` 隔离，调用方不能指定 owner；保存要求 revision，避免多窗口静默覆盖。响应严格限制字段和文本长度，拒绝危险对象键与未知命令。房间状态有上限，写操作按用户限频，登录/HTTP 有暖实例速率限制；如需防公网恶意大流量，需结合 CloudBase 网关限流与费用上限，暖实例限流不是全局 DDoS 防护。

## 登录与恢复

开发或无公众号部署的 guest 由浏览器生成 256 位 deviceSecret，服务端以稳定密钥派生身份；只使用微信授权的环境关闭 guest。微信授权使用精确 HTTPS 回调白名单、随机一次性 state、浏览器 verifier；云函数交换 code，OpenID 与 AppSecret 不发到客户端。会话有效 180 天，每次应用打开验证并刷新；服务器记录最近房间。本地只持久保存会话、deviceSecret、房间位置和 OAuth 临时校验数据，不缓存角色、任务选择或房间秘密。

前台轮询不写心跳，带版本减少返回体；后台停止调度，恢复前台/在线立即读状态，失败指数退避最多 30 秒。网络丢失导致结果不确定时，用户可重试同一请求 ID；刷新后直接读取已提交结果。服务器始终防止重复投票与跨阶段重放。清除 guest 浏览器存储无法恢复原 guest 身份；OpenID 则可重新认证。

## 部署后仍须验收

CloudBase Node SDK 当前依赖的独立 `lodash.set` 已停止维护，项目用 `vendor/lodash-set` 的兼容入口调用维护中的 lodash `set`。根项目与云函数包同时覆盖 axios / lodash.unset 到已修复版本，锁文件包含准确依赖。更新 SDK 时须保留或重新评估这些覆盖，并运行 `npm audit` 和存储适配器测试；不要直接使用未覆盖的临时云函数依赖清单。

自动化覆盖本地同源 API、纯状态机、CloudBase 存储适配器合同与浏览器流程。云数据库实际事务、网关 CORS、真实公众号权限、域名验证和微信 WebView 生命周期必须在自己的环境验证。仓库没有云凭据，也没有声称已在真实微信/云环境上线。
